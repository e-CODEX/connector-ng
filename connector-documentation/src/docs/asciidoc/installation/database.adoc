= Database Configuration

The application has been tested against the following database versions:

[cols="1,1", options="header"]
|===
| Database | Version

| MySQL | 8.4.9
| MariaDB | 12.3.2
| PostgreSQL | 17.0
| Oracle | 23
|===

An empty schema and a dedicated database user must exist before the first start.

== Create a database user with appropriate privileges

Because the application relies on distributed transactions (XA), the database user used to connect to the dedicated database must be granted the privileges required to execute and recover XA transactions.
The exact grant differs by vendor:

[cols="1,3", options="header"]
|===
| Database | Requirement

| MySQL
| Grant the `XA_RECOVER_ADMIN` privilege, for example `GRANT XA_RECOVER_ADMIN ON *.* TO 'connector'@'%';`

| MariaDB
| The user must be allowed to run `XA RECOVER`. See the MariaDB documentation for the privilege required by your version.
|===

NOTE: Some managed database offerings do not expose root/superadmin access and therefore cannot grant full XA recovery privileges (this is the case for some managed MariaDB instances).
In that situation, the application falls back to alternative transaction-handling strategies, with reduced recovery guarantees after a crash.

== Database initialization

To initialize the connector database, two options are available:

* Let the application initialize the database at startup
* Run the provided initialization scripts manually

=== Let the application initialize the database

Set the following property and launch the application:

[source,properties]
----
spring.jpa.hibernate.ddl-auto=update
----

The connector will automatically create the necessary tables on startup.

WARNING: This option is intended for development and testing only.
For production deployments, use the manual initialization scripts described below — `ddl-auto=update` is not a reliable mechanism for managing schema evolution over time.

=== Run the initialization scripts

Initialization scripts for each supported database are provided in the distribution package, under:

`dbscripts/initial`

Each supported vendor has its own script (e.g. `mysql.sql`, `mariadb.sql`,
`postgres.sql`, `oracle.sql`) containing the SQL scripts to execute against the target database before starting the application for the first time.

== Connection settings

The datasource must use the XA-capable driver of your database. In the Docker deployment these values are set with the
`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `DB_DRIVER_CLASSNAME` and `DB_DIALECT` variables.

[cols="1,2,2", options="header"]
|===
| Database | Driver class name | Hibernate dialect

| MySQL
| `com.mysql.cj.jdbc.MysqlXADataSource`
| `org.hibernate.dialect.MySQLDialect`

| MariaDB
| `org.mariadb.jdbc.MariaDbDataSource`
| `org.hibernate.dialect.MariaDBDialect`

| PostgreSQL
| `org.postgresql.xa.PGXADataSource`
| `org.hibernate.dialect.PostgreSQLDialect`

| Oracle
| `oracle.jdbc.xa.client.OracleXADataSource`
| `org.hibernate.dialect.OracleDialect`
|===

== Upgrading

=== Upgrading from 6.x

The 7.x release changes the database schema. Do not start the 7.x connector against a 6.x database.

=== Upgrading from 7.0.0

No member state has deployed connector 7.0.0 in production. If you are coming from version 7.0.0,
recreate the database from scratch instead of upgrading it:

. Stop the connector.
. Drop the existing schema and create a new, empty one (or use a new database).
. Initialize it again as described in <<Database initialization>>.
. Start the connector.

WARNING: Recreating the database deletes all data of the previous installation. Back up anything
you need to keep before you drop the schema.
