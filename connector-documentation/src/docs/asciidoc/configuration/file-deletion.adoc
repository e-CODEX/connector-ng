= File cleanup

== Orphaned attachments cleanup

An attachment is *orphaned* when it is not linked to any message (`MESSAGE_ID` is `null`).
This happens, for example, when a file was uploaded but the message it belonged to was never created.

A scheduled job periodically looks for orphaned attachments that are older than a configurable
threshold, deletes their content from the file storage (for example the S3 bucket), and then marks
them as deleted in the database by setting `DELETED_AT`.

=== Basic configuration
Configuration is provided via `application.properties` under the `connector.file-deletion.*` prefix.

[cols="3,4,1,3", options="header"]
|===
| Property | Description | Optional | Example

| `connector.file-deletion.orphan.threshold`
| Minimum age of an orphaned attachment before its file is deleted.
The age is computed from the attachment creation date (`CREATED_AT`, stored in UTC).
Accepts durations such as `30m`, `12h`, `1d` or ISO-8601 (`PT36H`).
| Yes (default: `1d`)
| `connector.file-deletion.orphan.threshold=1d`

| `connector.file-deletion.orphan.cron`
| Schedule of the cleanup job, as a Spring cron expression with six fields
(second, minute, hour, day of month, month, day of week).
Set to `-` to disable the job.
| Yes (default: `0 0 0 * * *`)
| `connector.file-deletion.orphan.cron=0 0 0 * * *`
|===

.Configuration Example
[source,properties]
----
# Delete the files of orphaned attachments that are at least 1 day old
connector.file-deletion.orphan.threshold=1d

# Run the cleanup every day at 00:00:00
connector.file-deletion.orphan.cron=0 0 0 * * *
----

NOTE: In a `.properties` file, do not wrap the cron expression in quotes: they would become part
of the value. In YAML, quotes are required because of the `*` characters.

=== Threshold format

The threshold accepts the standard Spring Boot duration formats:

[cols="1,2", options="header"]
|===
| Value | Meaning

| `30m` | 30 minutes
| `12h` | 12 hours
| `1d` | 1 day
| `PT36H` | 36 hours (ISO-8601)
|===

A value without a unit (for example `60`) is interpreted as milliseconds.

=== Behavior

* Only attachments with no linked message and no deletion date are processed.
* The file is deleted from the storage first. The attachment is marked as deleted in the database
only after the deletion succeeded.
* If the deletion of one file fails, the error is logged, the other attachments are still
processed, and the failed attachment is retried at the next run.
* The job is idempotent: running it several times, or on several nodes at the same time, leads to
the same result. Deleting a file that no longer exists is not an error.

NOTE: With a threshold of `1d` and a daily schedule, an orphaned attachment is deleted between
24 hours and almost 48 hours after its creation, depending on when it was created relative to the
next run.

WARNING: Deleted files cannot be recovered.
