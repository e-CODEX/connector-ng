= Connector Queue Configuration

This configuration defines the internal messaging queues used by the connector platform for asynchronous message processing.

The queues coordinate the processing lifecycle for:

* Outbound messages
* Inbound messages
* Evidence generation
* Backend delivery
* Message staging and transport
* Cleanup of resolved messages

The queues are JMS queues provided by the external Apache ActiveMQ broker configured under
`spring.activemq.*`.

== Basic configuration
Configuration is provided via `application.properties` under the `connector.queues.*` prefix.
All properties are optional: when a property is not set, its default value is used.
Queue names must not be blank.

.Connector Queue Configuration Properties
[cols="35,40,10,15"]
|===
| Property | Description| Optional | Example

| `connector.queues.outbound-message-staging-queue`
| JMS queue name where outbound messages are first staged/buffered before being picked up for further processing (e.g., signing, AS4 packaging) on their way out to the gateway.
| Yes
| By default, set to `connector.queues.outbound-message-staging-queue`

| `connector.queues.outbound-message-processing-queue`
| JMS queue name used for the main outbound message processing step — messages move here from the staging queue to be processed and sent toward the gateway partner.
| Yes
| By default, set to `connector.queues.outbound-message-processing-queue`

| `connector.queues.outbound-evidence-trigger-queue`
| JMS queue name that triggers generation of REM evidence (e.g., submission acceptance) for outbound messages.
| Yes
| By default, set to `connector.queues.outbound-evidence-trigger-queue`

| `connector.queues.inbound-message-staging-queue`
| JMS queue name where inbound messages are first staged/buffered before being picked up for further processing (e.g., signature verification) on their way to the backend.
| Yes
| By default, set to `connector.queues.inbound-message-staging-queue`

| `connector.queues.inbound-message-processing-queue`
| JMS queue name used to process incoming messages received from the gateway before delivery to the backend.
| Yes
| By default, set to `connector.queues.inbound-message-processing-queue`

| `connector.queues.inbound-evidence-trigger-queue`
| JMS queue name that triggers generation of REM evidence (e.g., delivery/non-delivery) for inbound messages.
| Yes
| By default, set to `connector.queues.inbound-evidence-trigger-queue`

| `connector.queues.backend-delivery-queue`
| JMS queue name used for the final delivery hop — pushing processed inbound messages onward to the backend partner's endpoint.
| Yes
| By default, set to `connector.queues.backend-delivery-queue`

| `connector.queues.resolved-message-cleanup-processing-queue`
| JMS queue name used for the cleanup of messages that have been resolved (confirmed or rejected).
| Yes
| By default, set to `connector.queues.resolved-message-cleanup-processing-queue`
|===

NOTE: The configuration is validated at startup. An empty value (for example
`connector.queues.backend-delivery-queue=`) counts as set to blank and stops the connector.
Remove or comment out the line to use the default.

.Configuration Example
[source,properties]
----
connector.queues.outbound-message-staging-queue=connector.queues.outbound-message-staging-queue
connector.queues.outbound-message-processing-queue=connector.queues.outbound-message-processing-queue
connector.queues.outbound-evidence-trigger-queue=connector.queues.outbound-evidence-trigger-queue
connector.queues.inbound-message-staging-queue=connector.queues.inbound-message-staging-queue
connector.queues.inbound-message-processing-queue=connector.queues.inbound-message-processing-queue
connector.queues.inbound-evidence-trigger-queue=connector.queues.inbound-evidence-trigger-queue
connector.queues.backend-delivery-queue=connector.queues.backend-delivery-queue
connector.queues.resolved-message-cleanup-processing-queue=connector.queues.resolved-message-cleanup-processing-queue
----

== Dead letter queues and replay

When a message still fails after `connector.activemq.address-settings.max-delivery-attempts`
deliveries, the connector hands it back to the broker, which moves it to a dead letter queue (DLQ).
The administration API reads the DLQ of each *connector* queue under the name
`<dlq-prefix><queue name>`, for example `ActiveMQ.DLQ.connector.queues.backend-delivery-queue`:

* `GET /api/v1/admin/jms/queues/stats` gives the number of pending and failed messages per queue.
* `GET /api/v1/admin/jms/queues/messages?queue=<queue>&dlq=true` lists the failed messages (headers
and properties only, never the body).
* `GET /api/v1/admin/jms/queues/messages/{messageId}?queue=<queue>&dlq=true` reads one message with
its body (`dlq=false`, the default, reads a pending message). The connector queues hold the JSON of
the connector messages, returned as a `payload` map, as are the entries of a map message sent by the
gateway; any other text is returned as `text`, and the other message types have no body. A body
larger than 64 KB is cut, returned as `text`, and flagged `truncated`. The message is only browsed,
never consumed. As the body may hold business data, it is restricted to administrators.
* `POST /api/v1/admin/jms/queues/dlq/messages/{messageId}/replay?queue=<queue>` replays one failed
message. It answers `204` when the message was replayed, `404` when it is not in the DLQ and `409`
when it could not be replayed.
* `POST /api/v1/admin/jms/queues/dlq/replay` replays a list of failed messages, up to 100 at once.
* `DELETE /api/v1/admin/jms/queues/dlq/messages/{messageId}?queue=<queue>` deletes one failed
message for good, so that it is never processed again. It answers `204` when the message was
deleted, `404` when it is not in the DLQ and `409` when it could not be deleted.

The replays send the failed messages back to their queue, so that they are processed again, and are
restricted to administrators, as is the deletion. The list replay takes the queue and the message identifiers, and
answers with the outcome of each one:

[source,json]
----
{
  "queue": "connector.queues.backend-delivery-queue",
  "messageIds": ["ID:host-12345-1:1:1:1:1"]
}
----

The response lists the message identifiers which were `replayed`, which were `notFound` in the DLQ
and which `failed`: one failure does not stop the others. A message which cannot be replayed stays
in the DLQ. A replay is at-least-once: each message is first sent back to its queue and then
removed from the DLQ, so if the removal fails the message may be delivered again. Only text and map
messages, the types used by the connector, can be replayed.

The DLQ of the gateway queues can be listed but its messages can be neither replayed nor deleted:
the connector does not manage how the gateway dead-letters its messages, so such a request on a
gateway queue is refused with `400`.

=== Broker configuration

By default, ActiveMQ does *not* create one DLQ per queue: every failed message goes to the single
shared `ActiveMQ.DLQ` queue. To have a DLQ per connector queue, add this entry to the `policyEntries`
of the broker configuration (`activemq.xml`):

[source,xml]
----
<policyEntry queue="connector.queues.>">
  <deadLetterStrategy>
    <individualDeadLetterStrategy queuePrefix="ActiveMQ.DLQ."
                                  useQueueForQueueMessages="true"
                                  processExpired="false"/>
  </deadLetterStrategy>
</policyEntry>
----

The entry only matches the queues whose name starts with `connector.queues.`. It can be added next to
the entries of a broker shared with the gateway: ActiveMQ applies the most specific entry, so the
gateway queues keep the dead letter strategy they already have (for example the shared `domibus.DLQ`
of the Domibus configuration). Keep the `connector.queues.` prefix on the connector queue names, or
adapt the `queue` attribute to the names configured under `connector.queues.*`.

A sample broker configuration is provided in `docker/activemq/conf/activemq.xml` and is mounted by
the `activemq` service of `docker-compose.yml`.

.Dead letter queue properties
[cols="40,45,15"]
|===
| Property | Description | Default

| `connector.activemq.address-settings.dlq-prefix`
| Prefix of the per-queue DLQs. It must match the `queuePrefix` of the broker's
`individualDeadLetterStrategy`. Must not be blank.
| `ActiveMQ.DLQ.`
|===
